# Chisel ↔ SystemVerilog

Every design in this tutorial can be turned into synthesizable **SystemVerilog**,
and reading that output is one of the fastest ways to understand what Chisel
actually built. This file is the cross-chapter reference for that: what each
Chisel construct becomes, which parts of the generated file are real hardware
and which are simulation scaffolding, and what the output proves about the
book's claims that different coding styles describe the *same* circuit.

It is a companion to [`SCALA-NOTES.md`](SCALA-NOTES.md), which covers the other
side of the language — the Scala that runs at elaboration time.

*Conventions: paths are relative to the tutorial root. Every SystemVerilog block
below is **real captured output** from the chapter projects, generated with
Chisel 6.5.0 / CIRCT `firtool-1.62.0`. Source-locator comments are stripped for
readability (see [§B.3](#b3-stripping-the-noise)).*

## A. Generating the SystemVerilog

Every chapter has an entry point that writes `.sv` files into `generated/`:

```
$ sbt "runMain Generate"
```

Chapter 10 additionally takes names, because it has many designs:

```
$ sbt "runMain Generate list"                 # show what is available
$ sbt "runMain Generate UseAdder ParamFunc"   # just these two
```

### A.1 `emitVerilog` and the target directory

`emitVerilog` takes the design and an array of **Chisel** command-line options.
`--target-dir` is what decides where the file lands; without it every file is
written to the project root.

`ch05-combinational-building-blocks/src/main/scala/Generate.scala`
```scala
val opts = Array("--target-dir", "generated")

emitVerilog(new EncDec(), opts)
emitVerilog(new Comparator(), opts)
```

The file is named after the **emitted Verilog module**, not the Scala file — so
`emitVerilog(new Comparator())` writes `Comparator.sv`.

> **Verilog has no namespaces.** Two Chisel classes in different Scala packages
> can still emit the same module name and overwrite each other's `.sv`. Chapter
> 11 has exactly this: a top-level `BubbleFifo` and a `fifo.BubbleFifo`. Its
> `Generate` sends the package family to `generated/fifo/` to keep them apart.

### A.2 `.sv`, not `.v`

The book (written against an older Chisel) says `emitVerilog` produces `.v`.
Chisel 6 goes through CIRCT/firtool and emits **SystemVerilog**, so every file
in this tutorial is `.sv`. Most of them genuinely need an SV-capable tool —
packed arrays, `automatic`, `'{...}` array literals — though the register idiom
itself stays Verilog-2001 style. [§B.5](#b5-verilog-2001-or-systemverilog)
measures exactly which designs fall on which side.

## B. Anatomy of a generated file

A generated file has three parts, and only one of them is your circuit.

### B.1 The header and source locators

```
// Generated by CIRCT firtool-1.62.0
module Combinational(	// src/main/scala/Combinational.scala:4:7
  input        clock,	// src/main/scala/Combinational.scala:4:7
               reset,	// src/main/scala/Combinational.scala:4:7
  input  [3:0] io_a,	// src/main/scala/Combinational.scala:5:14
```

Every line carries a `file:line:column` comment pointing back at the Chisel that
produced it. This is the single most useful debugging feature of the output —
when synthesis complains about a signal, the comment tells you which line of
Scala created it.

### B.2 The randomization preamble

Sequential designs open with ~40 lines of preprocessor definitions:

```
`ifndef RANDOMIZE
  `ifdef RANDOMIZE_REG_INIT
    `define RANDOMIZE
  `endif // RANDOMIZE_REG_INIT
`endif // not def RANDOMIZE
...
```

and each register gets a matching `initial` block:

```
  `ifdef ENABLE_INITIAL_REG_
    initial begin
      automatic logic [31:0] _RANDOM[0:0];
      `ifdef RANDOMIZE_REG_INIT
        _RANDOM[/*Zero width*/ 1'b0] = `RANDOM;
        cntReg = _RANDOM[/*Zero width*/ 1'b0][7:0];
      `endif // RANDOMIZE_REG_INIT
    end // initial
  `endif // ENABLE_INITIAL_REG_
```

This is **simulation scaffolding, not hardware**. It optionally fills registers
with random values at time zero so that a testbench cannot accidentally pass by
relying on registers that happen to start at 0 in simulation but are undefined
on real silicon. It is wrapped in `` `ifndef SYNTHESIS `` and disappears during
synthesis. Skip it when reading — the circuit starts at `module`.

### B.3 Stripping the noise

To read the circuit alone, pass firtool's `-strip-debug-info` through
`ChiselStage`. Note this is a **firtool** option, not a Chisel one — passing
`--strip-debug-info` to `emitVerilog` fails with `Unknown option`:

*illustrative*
```scala
import circt.stage.ChiselStage

val sv = ChiselStage.emitSystemVerilog(
  new Combinational(), firtoolOpts = Array("-strip-debug-info"))
println(sv)
```

which yields exactly the circuit:

```
module Combinational(
  input        clock,
               reset,
  input  [3:0] io_a,
               io_b,
               io_c,
  output [3:0] io_out,
               io_out2
);

  wire [3:0] e = io_a & io_b | io_c;
  assign io_out = e;
  assign io_out2 = ~e;
endmodule
```

`ch10-hardware-generators/src/main/scala/FunctionalMin.scala` uses this to
compare four implementations side by side.

> **Import gotcha.** If `chisel3.util._` is also in scope it shadows the
> top-level `circt` package, and `import circt.stage.ChiselStage` fails with
> *object stage is not a member of package chisel3.util.circt*. Write
> `import _root_.circt.stage.ChiselStage` instead — which is why
> `FunctionalMin.scala` spells it that way.

### B.4 Why it does not look like SystemVerilog you would write

If you have written SystemVerilog by hand, or worked through an SV tutorial, the
generated code will look subtly archaic. Two constructs you were taught to
always reach for are **completely absent**. Across all 73 `.sv` files this
tutorial generates:

| construct | occurrences |
|---|---|
| `always @(posedge …)` | 136 |
| `always_ff` | **0** |
| `always_comb` | **0** |

Registers come out as `reg` in a plain `always @(posedge clock)` block, never
`logic` in an `always_ff`. This is not a version quirk of one design — it is the
whole corpus.

**It is not that firtool cannot.** The strings `always_ff`, `always_comb`, and
`always_latch` are all present in the firtool binary; they belong to CIRCT's
`sv` dialect, which a hand-built design can target. The Chisel → FIRRTL → SV
lowering path simply does not produce them. Nor is any flag responsible: the
output is unchanged under `--disable-all-randomization`,
`--emit-separate-always-blocks`, `--lowering-options=disallowLocalVariables`,
`--lowering-options=noAlwaysComb`, and `--lowering-options=verifLabels`.

`always_comb` is absent for a second, simpler reason: firtool barely uses
procedural combinational blocks at all, preferring continuous `assign`. Even a
dynamically indexed `Vec` write — the textbook case for a procedural block —
comes out fully unrolled:

*illustrative*
```scala
val v = WireDefault(VecInit(Seq.fill(8)(0.U(8.W))))
v(io.idx) := io.din
io.dout := v
```

```
  assign io_dout_0 = io_idx == 3'h0 ? io_din : 8'h0;
  assign io_dout_1 = io_idx == 3'h1 ? io_din : 8'h0;
  ...
  assign io_dout_7 = (&io_idx) ? io_din : 8'h0;
```

**Why this is a reasonable choice.** `always_ff` and `always_comb` are
*authoring* constructs. Their value is making the tool check a human's intent —
"you said flip-flop, did you write one?", and for `always_comb`, "did you forget
a branch and infer a latch?" Both checks are redundant here: the generator
already guarantees the intent, and Chisel catches the incomplete-assignment case
earlier and with a better message, at generation time
(see [§L](#l-things-chisel-will-not-generate)). What remains is `always_ff`'s
cost — it imposes SystemVerilog's single-driver restriction on every variable it
writes, constraining what the emitter may do elsewhere in the same file.

*(That last paragraph is design rationale, not measurement. What is measured
here is that firtool never emits these on the FIRRTL path and that no flag
changes it; CIRCT's own stated motivation is not documented in this tutorial.)*

### B.5 Verilog-2001 or SystemVerilog?

Both, in different places — and the split is worth knowing before you hand the
output to a tool.

The **register and logic idiom** is Verilog-2001 style: `always @(posedge)`,
`reg`, `wire`, `assign`. But the file as a whole is not Verilog-2001. Of the 73
generated files, **51 contain at least one SystemVerilog-only construct** —
packed multi-dimensional arrays (`wire [127:0][7:0]`), `'{...}` assignment
patterns, and `automatic logic` in the randomization blocks.

Stripping the simulation-only scaffolding with `--disable-all-randomization`
separates the two cleanly:

| design | SV-only constructs in the RTL | verdict |
|---|---|---|
| `UpTicker` (and the counters, `Arbiter3`, `Arbiter3Loop`) | none | **Verilog-2001 compatible** |
| `BcdTable`, `GenHardware` | packed array + `'{...}` for the ROM table | needs SystemVerilog |
| `RegisterFile` | packed array for the `Vec` | needs SystemVerilog |
| `ArbiterTree` | `automatic logic` remains even with randomization off | needs SystemVerilog |

The pattern: plain sequential and combinational logic really does come out
Verilog-2001-clean, and the moment a design carries a ROM table or an indexed
`Vec`, firtool reaches for packed arrays and the file requires an
SV-capable tool.

Note this cuts against reading [§B.4](#b4-why-it-does-not-look-like-systemverilog-you-would-write)
as "the emitter targets old tools" — if it did, it would not emit packed arrays
either. The consistent reading is narrower: firtool avoids the construct that
*restricts* it (`always_ff`), while freely using constructs that merely
*express* something (packed arrays, assignment patterns).

The practical description is **"SystemVerilog with a Verilog-2001-flavored
register idiom."** That is more useful than either label alone, and it explains
why hand-written-SV examples of Chisel output look plausible but never match.

## C. The core mapping table

| Chisel | SystemVerilog | Notes |
|---|---|---|
| `class X extends Module` | `module X(...)` | always gains `clock` + `reset` ports |
| `class X extends RawModule` | `module X(...)` | no implicit clock/reset |
| `val io = IO(new Bundle { val a = ... })` | ports named `io_a` | the `io` field name becomes a prefix |
| `IO(Input(UInt(4.W)))` at top level | port `a`, no prefix | prefix comes from the field path |
| `Input(UInt(8.W))` | `input [7:0]` | width − 1 downto 0 |
| `Output(Bool())` | `output` (1 bit) | `Bool` is a 1-bit `UInt` |
| `val w = Wire(UInt())` / `WireDefault` | `wire`, or folded into `assign` | often optimized away entirely |
| `:=` | `assign` / non-blocking `<=` | depends on combinational vs. registered |
| `RegInit(0.U)` | `reg` + `always @(posedge clock)` with reset | |
| `RegNext(x)` | `reg` updated unconditionally | |
| `when` / `.elsewhen` / `.otherwise` | nested `?:` or `if/else` | a priority multiplexer chain |
| `Mux(c, a, b)` | `c ? a : b` | |
| `switch` / `is` | indexed constant array, or `if/else` | see [§K.2](#k2-arbiters-generator-vs-handwritten-vs-truth-table) |
| `Module(new Sub())` | module instantiation | one file holds the whole hierarchy |
| `Vec(n, T)` | `_0`, `_1`, … flattened ports | no arrays at the port boundary |
| `Bundle` | `_`-joined field names | purely a naming convention in Verilog |
| `Mem` / `SyncReadMem` | a separate `mem_<depth>x<width>` module | see [§H](#h-memories) |
| a Scala `for` loop | nothing — its *result* is emitted | see [§J](#j-what-elaboration-erases) |

## D. Combinational logic

### D.1 Expressions

Chisel operators map to Verilog operators almost one-to-one, and named
intermediate values survive as `wire`s when they are used more than once.

`ch05-combinational-building-blocks/src/main/scala/Combinational.scala`
```scala
val e = (a & b) | c   // a named Boolean expression
val f = ~e            // reused in another expression

io.out := e
io.out2 := f
```

```
  wire [3:0] e = io_a & io_b | io_c;
  assign io_out = e;
  assign io_out2 = ~e;
```

Note that `f` did **not** become a wire — it is used once, so it was folded into
the `assign`. Chisel's parentheses are gone too: `&` binds tighter than `|` in
Verilog, so the expression is emitted unparenthesized.

Note also the `clock` and `reset` ports on a module with no state at all. Every
`Module` gets them whether or not it uses them; `RawModule` is the opt-out:

*illustrative*
```scala
class TmpRaw extends RawModule {
  val a = IO(Input(UInt(4.W)))
  val b = IO(Input(UInt(4.W)))
  val z = IO(Output(UInt(4.W)))
  z := a & b
}
```

```
module TmpRaw(
  input  [3:0] a,
               b,
  output [3:0] z
);

  assign z = a & b;
endmodule
```

Two differences at once: no `clock`/`reset`, and the ports are `a`/`b`/`z`
rather than `io_a`/`io_b`/`io_z`, because they were declared directly instead of
inside a bundle named `io`.

### D.2 `when` is a multiplexer

The single most important thing the generated code teaches: `when` is **not** a
statement that executes. It is a multiplexer.

`ch05-combinational-building-blocks/src/main/scala/Combinational.scala`
```scala
val w = Wire(UInt())

w := 0.U
when (cond) {
  w := 3.U
}
io.out := w
```

```
  assign io_out = {2'h0, {2{io_cond}}};
```

The wire and the default assignment are gone entirely, and there is not even a
multiplexer left. Because the two possible values are 0 (`4'b0000`) and 3
(`4'b0011`), selecting between them is the same as *replicating* `cond` into the
low two bits: `{2{io_cond}}` is Verilog's replication operator. The upper two
bits are constant in both cases.

That is worth dwelling on, because it is the general lesson. `when` is a
multiplexer *in the Chisel description*; whether a multiplexer survives into the
output is up to firtool's optimizer. Do not read the absence of a `?:` as
evidence that your `when` did something other than select a value.

### D.3 `elsewhen` is a priority chain

`ch05-combinational-building-blocks/src/main/scala/Combinational.scala`
```scala
when (cond) {
  w := 1.U
} .elsewhen (cond2) {
  w := 2.U
} .otherwise {
  w := 3.U
}
```

```
  assign io_out = {2'h0, io_cond ? 2'h1 : {1'h1, ~io_cond2}};
```

Worth reading slowly, because firtool has been clever. The three results are 1,
2, 3 — all fitting in 2 bits, so the upper two bits are a constant `2'h0`. When
`cond` holds the answer is `2'h1`. Otherwise the value is 2 or 3, which differ
only in the low bit, so the low bit is `~cond2` and the high bit is constant 1.
The *priority* is still there — `cond` is tested first — but the multiplexer
chain has been algebraically minimized. This is normal: expect the output to be
logically equivalent to your description, not structurally identical to it.

## E. Registers

`RegInit` becomes a `reg` with a synchronous reset in an `always @(posedge clock)`
block.

`ch06-sequential-building-blocks/src/main/scala/Counter.scala`
```scala
class WhenCounter(n: Int) extends Counter(n) {
  val N = (n - 1).U

  val cntReg = RegInit(0.U(8.W))
  cntReg := cntReg + 1.U
  when(cntReg === N) {
    cntReg := 0.U
  }

  io.tick := cntReg === N
  io.cnt := cntReg
}
```

emitted at `n = 10`:

```
  reg  [7:0] cntReg;
  wire       io_tick_0 = cntReg == 8'h9;
  always @(posedge clock) begin
    if (reset)
      cntReg <= 8'h0;
    else if (io_tick_0)
      cntReg <= 8'h0;
    else
      cntReg <= cntReg + 8'h1;
  end
  assign io_cnt = cntReg;
  assign io_tick = io_tick_0;
```

Four things to notice:

- **The Scala `val` name becomes the Verilog signal name.** `cntReg` is not an
  artifact — naming your registers well makes the generated code readable, and
  makes synthesis timing reports point at something recognizable.
- **Reset is synchronous** and appears as the first branch. Chisel's default
  `Module` reset is a synchronous, active-high `Bool`.
- **The comparison is shared.** `cntReg == 8'h9` feeds both the counter's
  wrap-around and the `tick` output, so it is emitted once as a named wire.
- **The branch order is inverted relative to the source.** The Chisel says
  "increment, *then* zero it under `when`"; the Verilog tests the wrap-around
  *first* and increments in the `else`. This is Chisel's **last connection wins**
  rule made visible: a later `:=` overrides an earlier one, so a conditional
  assignment written after an unconditional one has higher priority. Reading the
  generated `if`/`else` chain is the easiest way to confirm you got the priority
  you intended.

### E.1 Registers you do not read do not exist

Chapter 6's `Registers` module declares four register forms, but only wires one
of them to an output:

`ch06-sequential-building-blocks/src/main/scala/Registers.scala`
```scala
  // A register that resets to 0.
  val reg = RegInit(0.U(8.W))

  val d = io.in
  // Connect an input and read the output just by name.
  reg := d
  val q = reg

  // RegNext: a register whose input is d (defined and connected in one step).
  val nextReg = RegNext(d)

  // RegNext with a reset value.
  val bothReg = RegNext(d, 0.U)

  io.out := reg
```

```
module Registers(
  input        clock,
               reset,
  input  [7:0] io_in,
  output [7:0] io_out
);
  reg [7:0] reg_0;
  always @(posedge clock) begin
    if (reset)
      reg_0 <= 8'h0;
    else
      reg_0 <= io_in;
  end
  assign io_out = reg_0;
endmodule
```

`nextReg` and `bothReg` are **gone**. Nothing reads them, so they are dead logic
and firtool deletes them — flip-flops and all. This is the concrete form of the
book's recurring caveat that unused hardware is "optimized away": if you go
looking in the output for a register you declared and cannot find it, the first
question is whether anything downstream actually consumes it.

### E.2 Names that collide with Verilog keywords

Look closely at the register's name: the Chisel `val reg` came out as `reg_0`.
`reg` is a reserved word in Verilog, so it cannot be a signal name, and firtool
renames it by appending a numeric suffix.

This is worth knowing because it is silent — no warning — and it makes a signal
harder to find in a synthesis report than a well-chosen name would be. The same
applies to `wire`, `module`, `input`, `output`, `always`, `assign`, `initial`,
`begin`/`end`, and the rest of the Verilog and SystemVerilog reserved lists
(the book's appendix tabulates them). Avoiding those words for Chisel `val`s
keeps your names intact all the way through to the emitted code.

## F. Modules, hierarchy, and parameterization

One `emitVerilog` call produces **one file containing the whole hierarchy** —
submodules are not separate files. This is why the tutorial does not emit a
`.sv` for every `Module` class: a submodule already appears inside its parent's
file.

Chapter 10's `UseAdder` instantiates the same parameterized adder twice, at
8 and 16 bits:

`ch10-hardware-generators/src/main/scala/ParamAdder.scala`
```scala
// The simplest parameterization: a bit width passed to the module constructor.
class ParamAdder(n: Int) extends Module {
  val io = IO(new Bundle {
    val a = Input(UInt(n.W))
    val b = Input(UInt(n.W))
    val c = Output(UInt(n.W))
  })

  io.c := io.a + io.b
}

// Instantiate two differently-sized adders from the same generator.
class UseAdder extends Module {
  val io = IO(new Bundle {
    val x = Input(UInt(16.W))
    val y = Input(UInt(16.W))
    val res = Output(UInt(16.W))
  })

  val add8 = Module(new ParamAdder(8))
  val add16 = Module(new ParamAdder(16))

  add16.io.a := io.x
  add16.io.b := io.y
  io.res := add16.io.c | add8.io.c

  add8.io.a := io.x
  add8.io.b := io.y
}
```

```
module ParamAdder(
  input  [7:0] io_a,
               io_b,
  output [7:0] io_c
);

  assign io_c = io_a + io_b;
endmodule

module ParamAdder_1(
  input  [15:0] io_a,
                io_b,
  output [15:0] io_c
);

  assign io_c = io_a + io_b;
endmodule

module UseAdder(
  ...
  ParamAdder add8 (
    .io_a (io_x[7:0]),
    .io_b (io_y[7:0]),
    .io_c (_add8_io_c)
  );
  ParamAdder_1 add16 (
    .io_a (io_x),
    .io_b (io_y),
    .io_c (_add16_io_c)
  );
```

**This is the key difference from Verilog parameters.** Verilog has one
`ParamAdder` module with a `parameter WIDTH`, resolved by the synthesis tool.
Chisel resolves the parameter at elaboration and emits **two distinct modules**,
`ParamAdder` and `ParamAdder_1`, each with fixed widths. The `_1` suffix is how
firtool disambiguates two elaborations of the same class. Instances keep the
Scala `val` names (`add8`, `add16`), and connections are by named port.

A consequence worth internalizing: a Chisel generator with a hundred distinct
parameter combinations emits a hundred Verilog modules. There is no
parameterized module left in the output — parameterization is a *generation*
feature, not an output feature.

## G. Aggregates: `Vec` and `Bundle` are flattened

Verilog ports cannot be arrays or structs, so Chisel flattens them by joining
names with `_`. Chapter 2's register file has an optional 32-element debug port:

`ch02-basic-components/src/main/scala/RegisterFile.scala`
```scala
val dbgPort = if (debug)
  Some(Output(Vec(32, UInt(32.W)))) else None
```

(emitted with `new RegisterFile(true)`, so the optional port is present — note
that the `if` is plain Scala, so with `debug = false` the ports simply do not
exist in the output, per [§J](#j-what-elaboration-erases))

```
  output [31:0] io_rs1Val,
                io_rs2Val,
                io_dbgPort_0,
                io_dbgPort_1,
                io_dbgPort_2,
                ...
                io_dbgPort_31,
```

`Vec` index → `_<n>` suffix; `Bundle` field → `_<name>`. Nesting composes, so a
`Vec` of `Bundle`s gives `io_port_3_valid`. The structure exists only in Chisel;
in Verilog it is a naming convention, which is exactly why the `io` prefix and
good field names matter.

## H. Memories

`SyncReadMem` does not become a `reg` array inside your module. It becomes a
**separate module** named for its geometry, instantiated by yours:

`ch06-sequential-building-blocks/src/main/scala/memory.scala`
```scala
val mem = SyncReadMem(1024, UInt(8.W))
```

```
module mem_1024x8(
  input  [9:0] R0_addr,
  input        R0_en,
               R0_clk,
  output [7:0] R0_data,
  input  [9:0] W0_addr,
  input        W0_en,
               W0_clk,
  input  [7:0] W0_data
);

  reg [7:0] Memory[0:1023];
  reg       _R0_en_d0;
  reg [9:0] _R0_addr_d0;
  always @(posedge R0_clk) begin
    _R0_en_d0 <= R0_en;
    _R0_addr_d0 <= R0_addr;
  end
  always @(posedge W0_clk) begin
    if (W0_en & 1'h1)
      Memory[W0_addr] <= W0_data;
  end
  assign R0_data = _R0_en_d0 ? Memory[_R0_addr_d0] : 8'bx;
endmodule

module Memory(
  ...
  mem_1024x8 mem_ext (
    .R0_addr (io_rdAddr),
    .R0_en   (1'h1),
    .R0_clk  (clock),
    .R0_data (io_rdData),
    .W0_addr (io_wrAddr),
    .W0_en   (io_wrEna),
    .W0_clk  (clock),
    .W0_data (io_wrData)
  );
endmodule
```

The generic `R0_*`/`W0_*` port naming (read port 0, write port 0) exists so the
memory can be **swapped for a technology macro**. FPGA and ASIC flows want their
own block-RAM or compiled-SRAM cells rather than an inferred `reg` array, and
isolating the memory in its own module with a regular interface is what makes
that substitution mechanical.

Note also the registered address (`_R0_addr_d0`): that is where `SyncReadMem`'s
one-cycle read latency comes from, and the `8'bx` on a disabled read is why
reading a memory with `en` low gives you undefined data rather than zero.

## I. Finite-state machines

A Chisel `ChiselEnum` state register plus a `switch` becomes an ordinary encoded
state register and an `if`/`else` chain:

`ch08-finite-state-machines/src/main/scala/SimpleFsm.scala`
```scala
  // The three states (ChiselEnum gives symbolic, binary-encoded state names).
  object State extends ChiselEnum {
    val green, orange, red = Value
  }
  import State._

  // The state register, reset to green.
  val stateReg = RegInit(green)

  // Next state logic: a switch over the state, with input-guarded transitions.
  switch (stateReg) {
    is (green) {
      when(io.badEvent) {
        stateReg := orange
      }
    }
    is (orange) {
      when(io.badEvent) {
        stateReg := red
      } .elsewhen(io.clear) {
        stateReg := green
      }
    }
    is (red) {
      when (io.clear) {
        stateReg := green
      }
    }
  }

  // Output logic: Moore output depends only on the state.
  io.ringBell := stateReg === red
```

```
  reg [1:0] stateReg;
  always @(posedge clock) begin
    if (reset)
      stateReg <= 2'h0;
    else if (stateReg == 2'h0) begin
      if (io_badEvent)
        stateReg <= 2'h1;
    end
    else if (stateReg == 2'h1) begin
      if (io_badEvent)
        stateReg <= 2'h2;
      else if (io_clear)
        stateReg <= 2'h0;
    end
    else if (stateReg == 2'h2 & io_clear)
      stateReg <= 2'h0;
  end
  assign io_ringBell = stateReg == 2'h2;
```

The symbolic state names are **gone** — `green`/`orange`/`red` became `2'h0`,
`2'h1`, `2'h2`. `ChiselEnum` assigns the encoding densely from zero in
declaration order. If a synthesis tool reports a state-machine warning about
`stateReg`, you have to map the number back to the name yourself; the
source-locator comments ([§B.1](#b1-the-header-and-source-locators)) are the
fastest way to do it.

Note the FSM's outputs are pure functions of `stateReg` — this is a Moore
machine, and the generated code shows it: `io_ringBell` depends only on the
register, never on an input.

## J. What elaboration erases

Scala control flow runs **during generation** and leaves no trace. Chapter 10's
BCD table is the clearest case:

`ch10-hardware-generators/src/main/scala/BcdTable.scala`
```scala
val table = Wire(Vec(100, UInt(8.W)))

// Convert binary i to BCD: tens digit in the upper nibble, ones in the lower.
for (i <- 0 until 100) {
  table(i) := (((i / 10) << 4) + i % 10).U
}

io.data := table(io.address)
```

```
  wire [127:0][7:0] _GEN =
    '{8'h0,
      8'h0,
      8'h0,
      ...
```

The `for` loop does not exist in the output. Neither does the division, the
modulo, or the shift. What survives is the **result**: a fully expanded constant
array, which synthesis turns into a ROM or logic. The Scala arithmetic ran once,
on the JVM, at generation time.

This is the entire premise of Chapter 10, visible in one file. In Verilog you
would write a separate script to emit this table; in Chisel the generator *is*
the hardware description. It is also the reason `if`/`for` in Chisel are not
hardware conditionals — for a runtime conditional you need `when` or `Mux`.

## K. Different style, identical hardware

The book repeatedly says that different coding styles describe the same circuit.
The generated SystemVerilog is where you can check that claim rather than take
it on faith. Each result below was produced by normalizing two `.sv` files
(strip comments, unify the module name) and diffing — the method is in
[§M](#m-diffing-two-designs-yourself).

### K.1 Counters: five styles, three distinct circuits

Chapter 6 writes the same counter five ways. Emitting all five at `n = 10`:

| Style | vs. `WhenCounter` | What differs |
|---|---|---|
| `MuxCounter` | **byte-identical** | nothing — `when` and `Mux` are the same hardware |
| `FunctionCounter` | identical but for one name | the register is called `testCounter`, from the Scala `val` |
| `DownCounter` | genuinely different | counts 9 → 0, and the register is **4 bits, not 8** |
| `NerdCounter` | genuinely different | no comparator at all — tests the sign bit |

The first two rows are the book's point made concrete: `when`/`.otherwise` and
`Mux` are two spellings of one multiplexer, and the choice is pure readability.

The last two are the more interesting result, because they show what *does*
change the hardware. `DownCounter` counts toward zero, so its register only has
to hold 9 and firtool infers a 4-bit register — half the flip-flops for the same
externally visible behavior:

```
  reg  [3:0] cntReg;
  wire       io_tick_0 = cntReg == 4'h0;
```

`NerdCounter` goes further and removes the comparator entirely. It counts down
past zero and tests the sign bit, so `tick` is a single wire off the register
rather than an equality comparison:

```
  reg [7:0] cntReg;
  always @(posedge clock) begin
    if (reset)
      cntReg <= 8'h8;
    else if (cntReg[7])
      cntReg <= 8'h8;
    else
      cntReg <= cntReg - 8'h1;
  end
  assign io_cnt = cntReg;
  assign io_tick = cntReg[7];
```

Compare `assign io_tick = cntReg[7];` with `WhenCounter`'s
`wire io_tick_0 = cntReg == 8'h9;`. That is a whole comparator saved — and the
cost is that the code needs a comment to be readable, which is exactly the
trade-off the chapter is about.

### K.2 Arbiters: generator vs. handwritten vs. truth table

Chapter 5 writes a 3-input priority arbiter three ways:

| Style | vs. `Arbiter3` (handwritten) |
|---|---|
| `Arbiter3Loop` (for-loop generator) | **identical** |
| `Arbiter3Direct` (truth table) | different structure, same function |

The generator result is the reassuring one. `Arbiter3Loop` builds the priority
chain with a Scala `for` loop, and emits precisely the chain that was written
out by hand:

```
  wire grant_1 = io_request[1] & ~(io_request[0]);
  assign io_grant = {io_request[2] & ~grant_1 & ~(io_request[0]), grant_1, io_request[0]};
```

Writing the generator costs nothing in hardware — and unlike the handwritten
version it scales to any number of inputs.

`Arbiter3Direct` spells the same function as an eight-row truth table with
`switch`/`is`, and that is *not* what it becomes:

```
  wire [7:0][2:0] _GEN =
    {{{2'h0, &io_request}}, {3'h2}, {3'h1}, {3'h4}, {3'h1}, {3'h2}, {3'h1}, {3'h0}};
  assign io_grant = _GEN[io_request];
```

A packed constant array indexed by the request — a lookup table, not a chain of
gates. Logically equivalent, structurally different, and it will synthesize
differently. This is the practical reason the chapter prefers the generator: the
truth table doubles in size with every added input, while the chain grows by one
gate.

### K.3 `WireDefault` is sugar

`CombWhen` (a `Wire` plus an explicit default assignment) and `CombWireDefault`
(`WireDefault` folding the two together) emit **identical** SystemVerilog. The
difference is only in how much you have to read.

## L. Things Chisel will not generate

- **No tri-state / high-impedance.** Chisel has no `Z` value, so an on-chip bus
  is built from multiplexers instead of shared bidirectional wires. See
  [Chapter 12](ch12-interconnect/README.md) — this is a deliberate restriction,
  not an omission, because tri-state buses are impractical on-chip anyway.
- **No `X` propagation in your description.** `X` appears only where firtool
  puts it, such as the `8'bx` on a disabled memory read in [§H](#h-memories).
- **No inferred latches.** In Verilog, a combinational `always` block that does
  not assign its target on every path infers a latch — usually a bug, and often
  a silent one. In Chisel the same mistake is a hard error: a `Wire` assigned
  only inside a `when`, with no default and no `.otherwise`, fails during
  generation with

  ```
  error: sink "w" not fully initialized in "TmpLatch"
    val w = Wire(UInt(4.W))
                ^
  ```

  Note this comes from firtool, not from the Scala compiler, so it surfaces when
  you emit rather than when you compile. `WireDefault` exists precisely to make
  the default case hard to forget.
- **No parameterized Verilog modules.** Parameters are resolved at elaboration;
  see [§F](#f-modules-hierarchy-and-parameterization).
- **No `initial` blocks that matter.** The generated `initial` blocks are the
  simulation-only randomization of [§B.2](#b2-the-randomization-preamble).
- **No delays, no `#`.** There is no notion of simulation time in a Chisel
  description; timing comes from the clock.

## M. Diffing two designs yourself

Two generated files that describe the same circuit will still differ in their
source-locator comments and module names, so a raw `diff` is useless. Normalize
first — strip comments, unify the module name, drop blank lines:

*illustrative*
```bash
norm() {
  sed -n '/^module/,/^endmodule/p' "$1.sv" \
    | sed -e 's|//.*||' -e "s/module $1/module M/" -e 's/[[:space:]]*$//' -e '/^$/d'
}

cd ch06-sequential-building-blocks/generated
diff <(norm WhenCounter) <(norm MuxCounter) && echo IDENTICAL
```

Every claim in [§K](#k-different-style-identical-hardware) was produced this way
and can be reproduced after `sbt "runMain Generate"`.

For counting rather than comparing,
`ch10-hardware-generators/src/main/scala/FunctionalMin.scala` shows the other
technique: emit to a string and count comparators, multiplexers, and wires.

## N. Simulation-only constructs

`printf`, `assert`, and `stop` are the three Chisel constructs that describe **no
hardware**. They emit SystemVerilog that exists only during simulation and
disappears at synthesis, and the shape of that code answers several questions
Chapter 13 raises.

### N.1 `assert` → `$error` / `$fatal`

`ch13-debugging-testing-verification/src/main/scala/Assert.scala`
```scala
class AssertOverflow extends Module {
  val io = IO(new Bundle {
    val a = Input(UInt(8.W))
    val b = Input(UInt(8.W))
    val sum = Output(UInt(8.W))
  })
  io.sum := io.a + io.b

  assert(io.sum >= io.a, "8-bit add must not overflow")
}
```

```
  wire [7:0] _io_sum_T = io_a + io_b;
  `ifndef SYNTHESIS
    always @(posedge clock) begin
      if (~reset & _io_sum_T < io_a) begin
        if (`ASSERT_VERBOSE_COND_)
          $error("Assertion failed: 8-bit add must not overflow\n    at Assert.scala:34 assert(io.sum >= io.a, \"8-bit add must not overflow\")\n");
        if (`STOP_COND_)
          $fatal;
      end
    end
  `endif // not def SYNTHESIS
  assign io_sum = _io_sum_T;
```

Four things to read here.

**The condition is inverted.** You assert `sum >= a`; the emitted code fires on
`_io_sum_T < io_a`. An assertion checks for the *failure*, so expect the negation.

**It carries your Chisel source location and the original expression text** into
the `$error` string. A failing assertion in a simulation log points at
`Assert.scala:34`, not at a line of Verilog — the most useful property of this
output.

**It is reset-gated** (`~reset &`). A design in reset is not expected to hold its
invariants. The same gating applies to `printf`, which is the usual explanation
for "my `printf` printed nothing" — check your reset duration first.

**`$error` and `$fatal` are separately gated**, by `` `ASSERT_VERBOSE_COND_ ``
and `` `STOP_COND_ ``, so a testbench can log failures without aborting.

### N.2 An assertion that cannot fail is not emitted

The chapter's other adder asserts a tautology — `io.sum` was *defined* as
`io.a + io.b`:

`ch13-debugging-testing-verification/src/main/scala/Assert.scala`
```scala
  assert(io.sum === io.a + io.b)
```

and its entire generated module is:

```
module Assert(
  input        clock,
               reset,
  input  [7:0] io_a,
               io_b,
  output [7:0] io_sum
);

  assign io_sum = io_a + io_b;
endmodule
```

**No assertion at all.** firtool proved it constant and deleted it. Before
concluding that an assertion is protecting you, check that it survived into the
output — a check that cannot fail is not a check.

### N.3 The SVA form

Formal tools do not consume `$error` calls; they consume **concurrent
assertions**. The same design, emitted with firtool's
`--emit-chisel-asserts-as-sva` (`sbt "runMain GenerateSva"` in Chapter 13):

```
  wire [7:0] _io_sum_T = io_a + io_b;
  wire       _GEN = reset | _io_sum_T >= io_a;
  assert__chisel3_builtin:
    assert property (@(posedge clock) _GEN)
    else $error("Assertion failed: 8-bit add must not overflow\n    at Assert.scala:34 assert(io.sum >= io.a, \"8-bit add must not overflow\")\n");
  `ifdef USE_PROPERTY_AS_CONSTRAINT
    assume__chisel3_builtin: assume property (@(posedge clock) _GEN);
  `endif // USE_PROPERTY_AS_CONSTRAINT
```

Same design, same assertion, a different contract with the tools:

- `assert property (...)` instead of an `if` inside an `always` block, and **no**
  `` `ifndef SYNTHESIS `` wrapper.
- The condition is **not** inverted this time — `_GEN` is the positive property,
  with reset-gating folded in as `reset | ...`.
- `USE_PROPERTY_AS_CONSTRAINT` lets the same property be re-used as an
  *assumption*, which is how you constrain a formal run.

If you hand RTL to a formal tool without this flag, your assertions ship as
`$error` calls the tool ignores.

### N.4 Multi-cycle properties

A Chisel `assert` is an **immediate** assertion — one condition, one clock edge.
SystemVerilog's temporal operators (`|->`, `##[1:2]`, `throughout`) describe
behaviour *over time*, and those cannot be written as an `assert`.

They **can** be written in Chisel, via `chisel3.ltl`:

*illustrative*
```scala
import chisel3.ltl._
import chisel3.ltl.Sequence.BoolSequence

AssertProperty(io.req.implication(io.grant.delayRange(1, 2)))
```

which emits genuine SVA — `io_req |-> ##[1:2] io_grant`, with a `disable iff`
guard firtool generates for you. So "Chisel cannot express SVA" is wrong;
"a Chisel `assert` cannot" is right.

### N.5 What your tests actually exercise

Worth restating here because it changes what all of the above means: with
ChiselTest's default **Treadle** backend, `sbt test` simulates **FIRRTL**, not the
SystemVerilog on this page. Switching to the Verilator backend runs the same test
code against the real emitted RTL. Chapter 13's
[§13.2](ch13-debugging-testing-verification/README.md#which-artifact-are-your-tests-actually-running)
covers the difference, the one-line change, and a verified toolchain caveat.

**Where Chisel test code stops.** Module-level verification is well covered, but
some things need a SystemVerilog or C++ testbench regardless:

- running software on a core — loading an ELF and simulating for millions of
  cycles is normally driven by a C++ or SV harness, for speed;
- UVM's constrained-random, coverage-driven machinery, which has no Chisel
  equivalent;
- gate-level simulation — after synthesis there is no Chisel and no FIRRTL, only
  a netlist;
- any design that must sit as a DUT inside an existing SV/UVM environment.
